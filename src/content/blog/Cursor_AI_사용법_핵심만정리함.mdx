Cursor는 VS Code를 기반으로 만들어진 AI 코드 에디터입니다.

기존 VS Code 기능과 확장 프로그램을 대부분 그대로 사용할 수 있고, Cursor 자체 모델뿐 아니라 GPT, Claude, Codex, Gemini 등 다양한 AI 모델을 별도의 복잡한 세팅 없이 선택해 사용할 수 있다는 것이 장점입니다.

처음에는 단순히 "VS Code에 AI가 붙은 에디터"처럼 보이지만, 실제로 사용해보면 모델 선택부터 Agent, Plan, MultiTask 같은 작업 모드, 프로젝트 규칙 관리까지 활용할 수 있는 기능이 꽤 많습니다.

이번 글에서는 Cursor를 사용할 때 알아두면 좋은 핵심 기능들을 정리해보겠습니다.

---

## 1. Cursor 기본 화면과 단축키

Cursor는 크게 **Agents Window**와 **IDE** 두 가지 형태로 사용할 수 있습니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g10-1.png" />

Agents Window는 ChatGPT나 Claude Desktop처럼 프롬프트 중심으로 AI와 작업하는 화면이고, 실제 파일과 코드를 직접 확인하면서 작업하려면 IDE 모드가 더 적합합니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g13.png" />

개발이나 퍼블리싱 작업에서는 보통 IDE 모드를 중심으로 사용하게 됩니다.

자주 사용하는 단축키도 몇 가지 알아두면 편합니다.

- ``Ctrl + `(벡틱)`` : 터미널 열기 / 닫기
- `Ctrl + L` : Cursor 대화창 열기 / 닫기
- `Ctrl + B` : 왼쪽 패널 열기 / 닫기
- `Ctrl + Shift + V` : 서식 없이 붙여넣기

특히 프롬프트에 Markdown이나 코드 내용을 붙여넣었을 때 일반 텍스트가 아니라 코드라인처럼 첨부되는 것이 불편하다면 `Ctrl + Shift + V`를 사용하면 됩니다.

## 2. Cursor에서 해두면 좋은 설정

VS Code 기반의 일반적인 에디터 설정은 기존 VS Code 사용 환경과 크게 다르지 않습니다.

여기서는 Cursor를 사용할 때 특히 의미 있는 두 가지 설정만 정리합니다.

### Git 커밋 메시지에서 Cursor 공동 작업자 문구 제거하기

Cursor에게 Git 커밋과 푸시까지 맡기면 커밋 메시지에 다음과 같은 공동 작업자 문구가 추가될 수 있습니다.

`Co-authored-by: Cursor <cursoragent@cursor.com>`

이 문구를 남기고 싶지 않다면 다음 경로에서 관련 설정을 변경할 수 있습니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g7-1.png" />

`Ctrl + ,` → **Cursor Settings** → **Git & PRs**

회사나 팀에서 별도의 커밋 메시지 규칙을 사용하고 있거나 AI 공동 작업자 정보를 커밋 로그에 남기고 싶지 않을 때 유용합니다.

### 사용자 승인 없이 명령 자동 실행하기

Cursor는 터미널 명령, MCP 연결, Git 작업 등을 실행하는 과정에서 사용자 승인을 요구할 수 있습니다.

매번 승인하는 과정이 번거롭다면 다음 경로에서 실행 방식을 변경할 수 있습니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g9.png" />

`Ctrl + ,` → **Cursor Settings** → **Agents** → **Execution and Approvals** → **Run Mode**

여기서 **Auto-Review를 Run Everything**으로 설정하면 MCP 연결이나 Git 명령 등을 사용자 승인 없이 자동으로 수행하도록 설정할 수 있습니다.

파일 수정부터 터미널, Git 작업까지 Cursor에게 연속해서 맡기는 경우 작업 흐름이 훨씬 자연스러워집니다.

다만 명령 실행 권한을 넓게 허용하는 설정인 만큼, 중요한 프로젝트에서는 Cursor가 실행하는 명령을 확인할 수 있는 환경에서 사용하는 편이 좋습니다.

#### 2-1. Cursor 모델 추가/삭제 하기

<AssetImage src="/2026/AI/09-04/ai/assets/images/g0-2.png" />

`Ctrl + ,` 로 커서 세팅을 열고, 좌측 Models 탭을 클릭하면 스위치 토글을 통해 원하는 모델을 추가/삭제 할 수 있습니다.

## 3. Cursor의 AI 모델

Cursor에서 제공하는 AI는 크게 두 종류로 구분할 수 있습니다.

- **Cursor Models**: Auto (Cost), Cursor Grok, Composer 등
- **Other Models**: GPT, Claude, Codex, Gemini 등

<AssetImage src="/2026/AI/09-04/ai/assets/images/g8.png" />

두 종류는 사용되는 크레딧도 구분되어 있으며, 할당된 크레딧을 모두 사용하면 이후 사용량에 따라 추가 비용이 발생할 수 있습니다.

여기서 주의할 점은 **Auto 라고 해서 모두 동일한 비용 구조를 사용하는 것은 아니라는 것**입니다.

Auto의 Balance와 Intelligence는 실제로 선택된 외부 모델의 사용량과 연결될 수 있기 때문에 단순히 이름에 Auto가 들어간다고 해서 무조건 저렴하다고 생각하면 안 됩니다.

Auto 모델에 대한 상세한 내용은 <a href="#5-auto-라우터" >5. Auto 라우터</a> 에서 확인할 수 있습니다.

## Effort

<AssetImage src="/2026/AI/09-04/ai/assets/images/g15.png" />

Auto 와 Composer 모델을 제외한 나머지 모델 (GPT, Claude, Grok 등) 들은 `Low`, `Medium`, `High`, `Extra High` 등으로 AI의 사고 깊이인 **Effort**를 설정할 수 있습니다.

Effort가 높을수록 복잡한 작업에서 정확도가 좋아질 수 있는 대신 결과가 나오는 속도도 느려집니다.

따라서 항상 가장 높은 값을 사용하는 것보다는 작업 규모에 맞춰 선택하는 것이 좋습니다.

단순 수정이라면 낮거나 중간 정도의 Effort로도 충분하고, 여러 파일의 구조를 분석하거나 복잡한 문제를 해결해야 할 때는 높은 Effort를 사용하는 식입니다.

### 3-1. 개인적인 AI 모델 사용 후기

여러 프로젝트에 도입하여 사용해보면서 느낀 점을 정리했습니다. (HTML/SCSS/JS 작업 기준)

⭐: 사용 추천 | ❌: 비추천 | ❓: 잘 모르겠음.

- ⭐ Auto (Cost): 피그마를 HTML로 변환, 폰트크기나 색상 수정, 파일명이나 클래스명 일괄 수정 등.
  단순 노동 작업이나 코드 분석이 크게 필요없는 작업에만 사용 중.
- ❌ Auto (Balance): 알아서 모델 지정 해주는건 편하지만, 비용적인 측면에서는 전혀 효율적이지 않음.
- ⭐ Composer 2.5: Auto (Cost) 보단 살짝 더 비싸긴 하지만 더 똑똑해서 가끔 Auto(Cost) 가 알아먹지 못할 때 사용 중.
  (HTML 변환 작업은 잘 되는데 공통 컴포넌트 구현은 성능이 좀 떨어지는 것 같음.)
- ⭐ Cursor Grok 4.6 Medium: 공통 컴포넌트 설계나 기능 구현, HTML/SCSS 코드 리팩토링 등. 메인으로 사용하는 모델. 비용도 그렇게 부담스럽지는 않은 편.
  <br/>
 > High의 경우는, 결과물은 잘 나오긴하나 생각이 많아서 그런지 속도가 너무 느림.
 개인적으로 High 옵션은 퍼블리싱 작업에 쓰기엔 너무 오버스펙이라 생각 함.
<br/>
- ❓ GPT-5.6 Sol Medium: 작업 요청을 하면 한 두번만에 의도한 결과물을 얻을 수 있어서 수정 요청을 크게 하지않음. 다만, 그만큼 비용은 조금 비싼 편이라 자주 사용하지는 않고 Grok으로 컴포넌트 구현이 잘 안될 때 수정용으로 사용하는 편. (개인 구독 GPT로 SCSS나 JS 리팩토링도 시도해봤는데, 전체적으로 다 평균 이상은 하는 것으로 보임.)
- ❌ Claude sonnet 5 / Opus 5: 전체 검수나 리뷰용으로 사용하였는데,
  정확도 자체는 다른 모델들에 비해 압도적으로 높은 편. (95%정도)

     <br/>
   > 그런데, 토큰을 엄청나게 잡아먹고 비용이 너무 비싸서 쓰기 두려운 모델.
   다른 모델들은 아무리 많이써도 **600만 토큰**까지 봤는데, **클로드 시리즈**는 기본 1000만부터 시작해서 심하면 **2000만 토큰 (20달러)** 까지 쓰는 경우가 있음.
   Opus가 과금이 특히 심하며, 가끔 중국어나 일본어를 섞어서 하는 경우도 있고,
   버그인지는 모르겠으나 1시간 내내 작업을 하는 상황도 있었음.
   <br/>

- ⭐ Codex : 기능 구현 / JS 리팩토링 용도로 사용 중. 스크립트 작업이나 리팩토링용으론 매우 좋음!
  그 외 화면 관련 작업은 비추천.

## 4. Auto 라우터

<AssetImage src="/2026/AI/09-04/ai/assets/images/g0-3.png" />

Auto는 사용자가 GPT나 Claude 같은 모델을 직접 지정하지 않아도 Cursor가 작업에 맞는 모델을 선택해주는 방식입니다.

작성일자 기준으로 Auto는 **Intelligence, Balance, Cost** 세 종류로 나뉩니다.

### Cost

비용 절약을 우선하는 모드로 3가지로 나뉘어지기 전, Auto 모델과 동일합니다.

단순한 코드 수정이나 반복 작업에 적합하며, 비용이 저렴한 대신 복잡한 코드 분석이나 리팩터링에서는 여러 번 수정 요청이 필요할 수 있습니다.

### Balance

품질과 비용 사이의 균형을 목표로 합니다.

Cursor가 작업 규모를 판단해 Composer, GPT, Claude 등 여러 모델 가운데 적절한 모델을 선택합니다.

결과물의 품질은 좋은 편이지만 고성능 모델이 선택되면 예상보다 비용이 많이 발생할 수 있으므로 사용량을 함께 확인하는 것이 좋습니다.

### Intelligence

성능과 품질을 우선하는 모드로, 복잡하고 여러 단계로 이어지는 고난도 작업에 적합합니다.

고성능 모델을 사용하는 만큼 비용도 실제 호출된 모델의 단가에 따라 발생합니다.

간단하게 정리하면 다음과 같습니다.

- **가벼운 수정·반복 작업 → Cost**

- **일반적인 개발 작업 → Balance**

- **복잡하고 정확도가 중요한 작업 → Intelligence**

## 5. 작업 모드: Agent, Plan, Ask

Cursor에서는 작업 목적에 따라 여러 작업 모드를 사용할 수 있습니다.

### Agent

가장 기본적인 모드입니다.

프롬프트에 작업을 요청하면 바로 코드 분석과 수정 작업을 시작합니다.

수정해야 할 내용과 범위가 명확할 때 사용하기 좋습니다.

### Plan

<AssetImage src="/2026/AI/09-04/ai/assets/images/g12-1.png" />

코드를 바로 수정하지 않고 먼저 작업 계획을 세우는 모드입니다.

AI가 작성한 계획을 검토한 뒤 **Build**를 눌러 실행하거나, 마음에 들지 않는 부분이 있다면 추가 프롬프트를 통해 계획부터 수정할 수 있습니다.

작업 규모가 크거나 여러 파일을 수정해야 하는 경우, AI가 요구사항을 제대로 이해했는지 먼저 확인하고 싶을 때 특히 유용합니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g12-2.png" />

또는 작업범위가 모호한경우, 사용자에게 오히려 질문을 던질 수도 있습니다.

### Ask

<AssetImage src="/2026/AI/09-04/ai/assets/images/g14.png" />

코드를 직접 수정하지 않고 질문에 대한 답변만 받는 모드입니다.

코드 검토, 누락된 내용 확인, 구현 방향 상담, 기존 코드에 대한 질문 등에 활용할 수 있습니다.

바로 수정시키기 애매한 작업이라면 먼저 Ask로 방향을 잡고 Agent나 Plan으로 넘어가는 방식도 유용합니다.

## 6. MultiTask와 병렬 작업

MultiTask는 여러 작업을 동시에 처리하기 위한 모드입니다.

다른 작업이 진행 중이더라도 별도의 작업을 비동기 Subagent로 실행할 수 있기 때문에 여러 작업을 병렬로 진행할 때 사용할 수 있습니다.

예를 들어 A 페이지를 수정하는 동안 B 페이지 작업을 동시에 진행하는 식입니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g-multi1.png" />

간단한 예시로, 위처럼 MultiTask 모드로 전환 후 새로운 스타일의 버튼을 만들어달라고 요청을 하였습니다.
동작 자체는 Agent 모드와 동일해보이지만, 실제 작업은 Sub Agent에서 진행되며, 최종 결과는 Main Agent (이 채팅창) 에서 확인할 수 있습니다.

"새 스타일 버튼 제작" 이라고 쓰여져있는 부분을 클릭하면 서브 에이전트가 어떠한 작업을 하고있는지 아래와 같이 확인이 가능합니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/g-multi2.png" />

작업 수행은 위처럼 서브 에이전트에서 진행되고, 작업이 종료되면 이 채팅은 닫히게 됩니다.

그런데, 이러한 기능에는 몇 가지 단점도 존재합니다.

<AssetImage src="/2026/AI/09-04/ai/assets/images/m1.png" />

첫 번째로, **MultiTask는 Agent보다 빠르지 않습니다.**

Cursor 공식 지원팀에 문의한 결과, MultiTask는 여러 작업을 병렬로 처리하기 위한 조정 과정이 있기 때문에 단순한 수정 하나만 수행한다면 일반 Agent가 더 직접적이고 빠를 수 있다고 합니다.

### 여러 Agent 채팅과 MultiTask의 차이

Agent 채팅을 여러 개 띄워 동시에 작업할 수도 있습니다.

이 경우 각각의 채팅은 독립된 컨텍스트를 가진 별도의 Top-level Agent로 동작합니다. 서로 완전히 독립적인 작업을 따로 관리하고 싶을 때 적합합니다.

반면 MultiTask는 하나의 작업 흐름 안에서 여러 요청을 Async Subagent로 나눠 병렬 처리하는 방식입니다.

Plan 모드 역시 이러한 병렬 처리 방식에 해당합니다.

쉽게 구분하면,

- **여러 Agent 채팅 = 독립된 작업자 여러 명**

- **MultiTask = 하나의 작업 안에서 여러 Subagent에게 일을 나눠 맡기는 방식**

이라고 이해할 수 있습니다.

### 병렬 작업 시 파일 충돌 주의

병렬 작업에서 가장 주의해야 할 부분입니다.

여러 Agent나 Subagent가 같은 파일을 동시에 수정하면 서로의 변경 내용을 덮어쓸 수 있으며, Cursor가 자동으로 작업 범위를 감지해 충돌을 막아주는 것은 아닙니다.

이를 방지하려면 Git Worktree를 이용해 각각 별도의 Checkout에서 작업하거나, 별도의 Cloud Environment로 작업 공간을 나누는 방법을 사용할 수 있습니다.

병렬 작업에서는 Agent를 많이 실행하는 것보다 **서로 겹치지 않게 작업 범위를 나누는 것**이 더 중요합니다.

## 7. AI에게 프로젝트 규칙 알려주기

Cursor를 계속 사용하다 보면 매번 같은 프로젝트 규칙을 프롬프트에 적는 것이 번거로워집니다.

새로운 사람이 프로젝트에 참여할 때마다 파일 구조나 작업 방식을 처음부터 다시 설명해야 하는 것과 비슷합니다.

이럴 때 `AGENTS.md`, Cursor Rules, Skills를 활용해 AI가 미리 참고해야 할 규칙과 작업 방법을 정리해둘 수 있습니다.

### AGENTS.md

프로젝트에서 AI가 따라야 할 기본 작업 규칙을 작성하는 안내문입니다.

프로젝트 루트나 특정 하위 폴더에 둘 수 있으며, 하위 폴더에 더 구체적인 내용이 있다면 해당 안내를 우선합니다.

쉽게 말하면 **프로젝트에 처음 들어온 사람에게 전달하는 기본 업무 안내서**와 비슷합니다.

"새 파일은 TypeScript로 작성하기", "이 폴더에서는 이 규칙 따르기"처럼 프로젝트에서 기본적으로 알아야 할 내용을 작성하는 용도입니다.

여기서 헷갈리기 쉬운 부분이 하나 있습니다.

**`AGENTS.md`와 `.agents` 폴더는 서로 다른 개념입니다.**

`AGENTS.md`는 프로젝트 규칙을 작성하는 Markdown 파일입니다. Cursor는 프로젝트 루트뿐 아니라 하위 디렉터리의 `AGENTS.md`도 지원하며, 더 구체적인 하위 규칙을 우선해서 적용할 수 있습니다.

반면 `.agents/`는 뒤에서 설명할 **Skills를 보관할 수 있는 경로**입니다. 따라서 `.agents`라는 이름 때문에 `AGENTS.md`를 그 안에 넣어야 하는 것은 아닙니다.

## Cursor Rules

`.cursor/rules`에 작성하는 Cursor 전용 규칙입니다.

모든 작업에 항상 적용하거나 특정 파일에서만 적용하는 등 규칙의 적용 범위를 조금 더 세밀하게 지정할 수 있습니다.

`AGENTS.md`가 프로젝트 전반의 안내문이라면 Cursor Rules는 **상황에 따라 적용되는 조금 더 구체적인 규칙**이라고 보면 이해하기 쉽습니다.

프로젝트 Rule은 `.cursor/rules/` 아래에 `.mdc` 파일로 작성할 수 있으며, 항상 적용하거나 특정 파일에서만 적용하는 등 범위를 설정할 수 있습니다.

개인적인 습관은 User Rules, 프로젝트 규칙은 `.cursor/rules`, 회사 공통 기준은 Team Rules처럼 분리해서 관리할 수도 있습니다.

> 단, 해당 폴더는 모든 AI가 아닌 **Cursor AI에 적용되는 규칙** 이라는 것을 기억해야 합니다.

## Skills

`SKILL.md`에는 특정 작업을 처리하는 방법과 순서를 정리할 수 있습니다.

필요한 스크립트, 예시, 서식 등을 함께 구성해두면 AI가 관련 작업을 수행할 때 참고할 수 있습니다.

Rules가 **이 규칙은 지켜야 한다**에 가깝다면 Skills는 **이 작업은 이런 방법과 순서로 처리한다**에 가깝습니다.

일상적으로 비유하면 Rules가 업무 규칙이라면 Skills는 특정 업무를 처리하는 **업무 매뉴얼**과 비슷합니다.

Cursor에서는 프로젝트 단위 Skill을 다음 두 경로에 둘 수 있습니다.

- `.agents/skills/`
- `.cursor/skills/`

각 Skill은 별도의 폴더 안에 `SKILL.md`를 두는 구조입니다. 두 경로 모두 Cursor에서 자동으로 인식됩니다.

## .agents와 .cursor 폴더의 차이

두 폴더는 이름이 비슷해 보이지만 역할을 구분해서 생각하는 편이 좋습니다.

`.agents/`는 특정 에디터에 종속되지 않고, 다양한 AI 에이전트 툴들 (GPT, Claude, Gemini, Grok 등) 이 공통으로 인식할 수 있도록 만든 표준화된 형태입니다.

```text
.agents/
└─ skills/
   └─ javascript/
      └─ SKILL.md
```

폴더 구조 구성은 위와같이 가능하며, Cursor에서도 `.agents` 폴더를 인식할 수 있습니다.

`.cursor/`는 Cursor 전용 프로젝트 설정과 관련된 파일들을 관리하는 공간에 가깝습니다.
즉, Cursor 외 다른 GPT나 Claude 같은 AI들은 인식할 수 없다는 의미입니다.

```text
.cursor/
├─ rules/
└─ skills/
```

폴더 구조 구성은 위와같이 가능합니다.

즉 Skills는 `.agents/skills/`와 `.cursor/skills/` 중 어느 쪽에 두어도 Cursor에서 인식되지만, **Cursor Rules는 `.cursor/rules/`에서 관리한다**는 차이가 있습니다.

쉽게 정리하면,

- **`AGENTS.md` = 프로젝트 기본 안내문**

- **`.agents/skills/` = Skills를 보관할 수 있는 경로**

- **`.cursor/rules/` = Cursor 프로젝트 규칙을 보관하는 경로**

- **`.cursor/skills/` = Cursor에서 사용할 Skills를 보관하는 또 다른 경로**

라고 이해하면 됩니다.

### 프로젝트 폴더 구조 예시

위 내용을 실제 프로젝트에 적용하면 대략 다음과 같은 형태로 구성할 수 있습니다.

```text
project/
│
├─ AGENTS.md
│
├─ .cursor/
│  └─ rules/
│     ├─ project.mdc
│     └─ javascript.mdc
│
├─ .agents/
│  └─ skills/
│     ├─ javascript/
│     │  └─ SKILL.md
│     │
│     └─ git/
│        └─ SKILL.md
│
├─ src/
│  ├─ js/
│  ├─ scss/
│  └─ html/
│
└─ ...
```

예를 들어 위 구조라면,

`AGENTS.md`에는 **프로젝트 전체에서 기본적으로 지켜야 할 내용**을 작성하고,

`.cursor/rules/javascript.mdc`에는 **JavaScript 작업 시 적용해야 할 세부 규칙**을 작성합니다.

그리고 `.agents/skills/javascript/SKILL.md`에는 **JavaScript 관련 특정 작업을 어떤 순서로 수행하고 검증할지**와 같은 작업 방법을 작성하는 식입니다.

Skills를 `.agents`가 아니라 `.cursor` 아래에서 관리하고 싶다면 다음처럼 구성해도 됩니다.

```text
project/
│
├─ AGENTS.md
│
├─ .cursor/
│  ├─ rules/
│  │  ├─ project.mdc
│  │  └─ javascript.mdc
│  │
│  └─ skills/
│     ├─ javascript/
│     │  └─ SKILL.md
│     └─ git/
│        └─ SKILL.md
│
└─ src/
   └─ ...
```

Cursor는 `.agents/skills/`와 `.cursor/skills/`를 모두 프로젝트 Skill 경로로 지원하므로 같은 Skill을 양쪽에 중복해서 만들 필요는 없습니다. 하나의 관리 방식을 정해서 사용하는 편이 깔끔합니다.

결국 역할을 기준으로 정리하면,

- **AGENTS.md = 프로젝트 전반의 기본 안내문**

- **Cursor Rules = 상황별로 적용되는 세부 규칙**

- **Skills = 특정 작업을 수행하는 방법과 절차**

정도로 구분하면 각각의 역할을 이해하기 쉽습니다.

## 8. Fast 옵션과 속도 저하

마지막으로 Cursor를 사용하면서 궁금했던 Fast 옵션과 속도 저하, Teams 플랜에 대해 Cursor 공식 지원팀에 문의한 내용을 정리해보겠습니다.

### Fast 옵션은 얼마나 비싼가?

<AssetImage src="/2026/AI/09-04/ai/assets/images/m2.png" />

Fast는 같은 모델의 결과를 더 빠르게 받기 위한 옵션으로 일반 모드보다 추가 비용이 발생합니다.

Cursor 공식 지원팀 답변 기준으로 대부분의 모델은 Standard 대비 약 **2배 정도의 토큰 단가**가 일반적인 기준이지만 모델마다 차이가 있습니다.

정확한 차이는 모델마다 다르지만, 기본적으로 추가 비용은 발생한다는게 핵심입니다.

제 개인적인 체감으로는 Fast를 썼을 때와 안 썼을 때의 차이를 느끼지 못해서 사용하지 않는 편이 비용관리에도 더 좋다고 생각합니다.

### 특정 시간대에 Cursor가 느려지는 이유

Cursor를 사용할 때 항상 4시부터 6시정도까지는 작업 속도가 현저히 느려지거나 (작업 한번에 약 20분정도) `try again` 같은 메시지가 나타나는 현상이 발생했습니다.

그러나 공식 답변에 따르면 특정 시간대에만 느려지거나 하는 현상은 없으며,

`try again` 같은 메시지가 나타나는 현상은 PC 사양보다는 서버 측 모델 수요가 높아진 경우와 관련될 가능성이 크다고 설명 했습니다.

이런 경우에는 Auto나 다른 모델로 변경하거나 동시에 실행 중인 Agent 요청 수를 줄이는 방법을 사용할 수 있다고 합니다.

### Teams 인원이 많으면 느려질까?

저희는 Teams 플랜을 결제하여 여러 명이 사용할 수 있도록 관리하고 있는데,

공식 답변으로는 Seat와 사용량은 멤버별로 관리되기 때문에 Teams 플랜의 인원이 많다고 해서 혹은 다른 팀원의 사용량이 내 모델의 처리 속도에 영향을 주거나 하진 않는다고 설명 했습니다.

다만 Cursor 전체 인프라에 사용량이 몰리는 경우에는 팀 규모와 관계없이 일시적인 속도 저하가 발생할 수 있다고 합니다.

## 결론

Cursor를 처음 사용하면 어떤 AI 모델이 가장 좋은지부터 고민하게 됩니다.

하지만 실제로 사용하다 보면 모델 자체보다 중요한 것은 **작업 성격에 따라 적절한 모델과 작업 방식을 선택하는 것**입니다.

간단한 수정은 Agent와 Cost를 이용하고, 작업 범위가 크다면 Plan으로 먼저 방향을 확인할 수 있습니다.

아직 구현 방향이 명확하지 않다면 Ask로 검토한 뒤 작업을 시작하고, 독립적인 작업이 여러 개라면 MultiTask나 여러 Agent를 활용해 병렬로 처리할 수도 있습니다.

프로젝트에서 반복적으로 지켜야 할 내용은 AGENTS.md와 Rules에 정리하고, 특정 작업의 처리 과정은 Skills로 만들어두면 매번 같은 내용을 설명하는 과정도 줄일 수 있습니다.

결국 Cursor는 단순히 코드를 대신 작성해주는 AI 도구라기보다는,

**AI에게 어떤 일을, 어떤 방식으로 맡길지 설계할 수 있는 개발 환경**

에 더 가깝다고 볼 수 있습니다.

모든 작업에 가장 강한 모델을 사용하는 것보다 작업의 난이도와 목적에 따라 **모델·작업 모드·프로젝트 규칙을 적절하게 조합하는 것**이 Cursor를 효율적으로 사용하는 핵심입니다.
